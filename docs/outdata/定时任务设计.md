# 定时任务架构设计

## 一、概述

本项目的定时任务系统用于在预定时间向用户推送消息或触发 AI 生成内容。采用**独立 asyncio loop** 实现，不依赖外部调度器（如 APScheduler 的 cron daemon），所有调度逻辑在进程内完成。

核心设计目标：
- 用户无需主动查询，agent 会在合适时机主动触达
- 任务类型多样：从简单提醒到需要 AI 实时生成的复杂内容
- 自适应频率——用户越活跃，主动打扰越少

## 三、核心模块详解

### 3.1 SchedulerService — 调度主循环

**文件**：`agent/scheduler.py`

基于 asyncio 的 tick 循环，每秒检查一次是否有任务到期。

#### 两种执行 tier

| Tier | 行为 | 适用场景 |
|------|------|----------|
| **instant** | 到点直接推送固定消息，零延迟 | 喝水提醒、吃药提醒 |
| **soft** | 到点触发 AI 生成实时内容，再推送 | 天气播报、新闻摘要 |

#### soft tier 的延迟自适应

soft 任务面临一个核心问题：用户期望 9:00 收到天气播报，但 AI 生成需要 25 秒。

解决方案——`LatencyTracker`（滑动窗口 P90 估算）：

```
用户期望到达时间: 09:00:00
AI 平均推理耗时:  ~25 秒
实际触发时间:     08:59:35（提前 P90 秒）
用户感知:         准时到达
```

- 滑动窗口 20 个样本，不足 3 个时回退默认值（25 秒）
- 模型变快会自动调整提前量，无需手动配置

#### 三种触发模式

| 模式 | 语义 | 示例 |
|------|------|------|
| `at` | 绝对时间 | `"14:30"`, `"2025-06-01T09:00"` |
| `after` | 相对延迟（从用户发消息时算） | `"30s"`, `"5m"`, `"2h"` |
| `every` | 循环（固定间隔或 cron） | `"1h"`, `"0 9 * * *"` |

`after` 模式支持 `request_time` 补偿——从用户发消息时刻计算延迟，而非从 AI 调用 tool 时刻计算，消除推理延迟的影响。

#### Misfire 恢复策略

进程可能在任务触发时宕机。重启后 `load_and_recover` 处理三种情况：

| 情况 | 处理 |
|------|------|
| `every` 类任务已过期 | 推进 `fire_at` 到下一个未来时间 |
| 一次性任务，错过 ≤ 5 分钟 | 保留，下次 tick 立即执行 |
| 一次性任务，错过 > 5 分钟 | 丢弃（避免"迟到 2 小时的喝水提醒"） |

#### 防重入机制

`_in_flight: set[str]` 追踪正在执行的任务 ID。tick 循环中跳过已 in-flight 的任务，防止 `every` 类任务在上一次执行未完成时重复触发。

### 3.2 ScheduledJob — 任务数据模型

```python
@dataclass
class ScheduledJob:
    trigger: str           # "at" | "after" | "every"
    tier: str              # "instant" | "soft"
    fire_at: datetime      # 下次名义触发时间（UTC）
    channel: str           # 目标渠道（telegram、qq 等）
    chat_id: str           # 目标会话 ID
    interval_seconds: int  # every + interval 模式
    cron_expr: str         # every + cron 模式
    message: str           # instant tier 的固定消息
    prompt: str            # soft tier 的 AI 提示词
    name: str              # 任务名（方便取消）
    timezone: str          # 时区
    run_count: int         # 已执行次数
    enabled: bool          # 是否启用
    id: str                # UUID
```

### 3.3 JobStore — 持久化

JSON 文件存储（`schedules.json`），序列化/反序列化 `ScheduledJob` 列表。启动时自动恢复，配合 misfire 宽限策略。

### 3.4 AI 工具接口

AI 通过三个 tool 管理定时任务：

| Tool | 功能 |
|------|------|
| `schedule` | 注册任务，指定 tier/trigger/when/channel/chat_id |
| `list_schedules` | 列出所有待执行任务 |
| `cancel_schedule` | 按 ID 或名称取消任务 |

### 3.5 循环依赖打破

`SchedulerService` 需要 `AgentLoop`（soft tier 调用 `process_direct`），而 `AgentLoop` 需要 `ToolRegistry`（其中包含 scheduler 的 tools）。

解决方案——`agent_loop_provider` 延迟解析：

```python
# 构造时传入 lambda，不立即解引用
scheduler = SchedulerService(
    agent_loop_provider=lambda: loop_ref.get("loop"),
    ...
)

# 执行时才实际获取 AgentLoop
def _get_agent_loop(self):
    return self._agent_loop_provider()
```

## 四、与其他系统的关系

### 4.1 与 ProactiveLoop（主动推送循环）的关系

两者是**平行子系统**，共享 `MessagePushTool` 作为交付通道，但调度逻辑独立：

| 维度 | SchedulerService | ProactiveLoop |
|------|------------------|---------------|
| 触发方式 | 固定时间（at/after/every） | 自适应能量模型 |
| 内容来源 | 预定义 prompt 或固定消息 | DataGateway 实时拉取 |
| 感知会话状态 | 不感知 | 有 passive_busy 检查 |
| 流量控制 | 无 | AnyActionGate 概率准入 |

### 4.2 与 Drift（空闲后台任务）的关系

Drift 是 ProactiveLoop 的子系统——当主动轮次拉取数据为空时触发。SchedulerService 和 Drift 没有直接关联。

### 4.3 统一架构图

```
┌──────────────────────────────────────────────────────────────┐
│                     MessagePushTool                           │
│               （统一的出站消息通道）                             │
└────▲──────────────▲──────────────▲───────────────────────────┘
     │              │              │
     │              │              │
┌────┴────┐  ┌──────┴──────┐  ┌───┴────────────┐
│Scheduler│  │ProactiveLoop│  │  被动 loop       │
│Service  │  │（能量模型驱动）│  │（用户消息触发）   │
│（定时驱动）│  │  ├─ Gate    │  │                 │
│         │  │  ├─ Fetch   │  │                 │

└─────────┘  │     ├       │  └─────────────────┘
             │     ▼       │
             │  Drift      │
             │（空闲后台任务）│
             └─────────────┘
```

## 五、当前架构的优势

### 5.1 深模块设计

`SchedulerService` 接口小（`add_job` / `cancel_job` / `list_jobs` / `run` / `stop`），行为多（tick 循环、双层执行、misfire 恢复、cron 推进）。通过 deletion test：删掉这个模块，复杂度会散落到多个调用方。

### 5.2 测试友好的 seam 设计

- `_now_fn` 注入：所有时间逻辑确定性可测，不依赖 wall clock
- `push_tool` / `agent_loop` 通过构造函数注入，测试用 `AsyncMock` 替换
- `LatencyTracker` 独立可测

### 5.3 自适应预触发

P90 延迟自适应比硬编码提前量更健壮。模型升级后推理变快，系统自动调整，无需人工干预。

### 5.4 循环依赖处理干净

`agent_loop_provider` lambda 延迟解析，避免了构造顺序耦合，保持模块职责单一。

## 六、当前架构的缺陷

### 6.1 ScheduledJob 不变量未守护

`trigger` 和 `tier` 是裸字符串，`message` 和 `prompt` 互斥但类型系统不约束。合法状态空间比类型表达的大，每新增消费 Job 的地方都要重新理解哪些字段组合合法。

### 6.2 JobStore 非原子写

使用 `save_json` 而非已有的 `atomic_save_json`。进程被 kill 时可能写一半文件，导致任务丢失——尤其是 `every` 类 recurring job，丢了意味着提醒永久消失。

### 6.3 soft 任务失败静默

`asyncio.create_task` 的异常只被 `logger.error` 记录，没有回调、没有重试、没有 dead letter。用户永远不会知道"9 点的天气播报"失败了。

### 6.4 无会话状态感知

SchedulerService 不检查用户是否正在对话中。soft 任务生成的内容直接 push，可能打断用户的实时对话——这是下一章要解决的核心问题。

### 6.5 bootstrap 层缺少集成测试

`build_scheduler()`、`SchedulerToolsetProvider.register()`、`agent_loop_provider` 的组装逻辑没有测试。改了依赖组装顺序不会被发现。

## 七、并发交付策略演进

### 7.1 问题场景

```
09:00:00  SchedulerService 触发 soft 任务"播报今日新闻"
09:00:25  AI 生成完毕，准备推送
08:58:00  用户正在和 agent 聊天（被动 loop 活跃中）
09:00:25  新闻推送突然出现在聊天流中 ← 打断用户
```

### 7.2 方案对比

| 方案 | 行为 | 上下文影响 | 用户体验 |
|------|------|-----------|---------|
| **A. 即时交付**（当前） | 生成后直接 push | 无 | 可能打断对话 |
| **B. 择机交付** | 检测 passive busy，空闲时再 push | 无 | 不打断，但延迟 |
| **C. 注入对话** | 内容注入当前会话上下文 | **污染上下文** | 语义混乱 |

**方案 C 不可行**——将 scheduler 内容注入当前对话会导致：
- token 浪费（无关内容占用上下文窗口）
- 语义漂移（LLM 在无关回复中提及新闻内容）
- 角色混乱（推送语气与助手语气混在一起）

### 7.3 推荐方案：交互式交付（方案 B+C 的中和）

核心思想：**交付但不侵入，由用户决定是否展开**。

```
┌─ scheduler 生成内容 ─────────────────────────────┐
│                                                    │
│  09:00:26  push 到 Telegram:                       │
│  ┌──────────────────────────────────────────┐      │
│  │ 今天有三条重要新闻：                       │      │
│  │ 1. xxxxx                                 │      │
│  │ 2. xxxxx                                 │      │
│  │ 3. xxxxx                                 │      │
│  │                                          │      │
│  │ 想聊聊哪条？  [感兴趣] [跳过]              │      │
│  └──────────────────────────────────────────┘      │
│                                                    │
│  这条消息 ← 不进入被动对话上下文                    │
│  用户点 [感兴趣] → 开新 session / 独立上下文        │
│  用户点 [跳过]   → 无事发生，不消耗任何上下文        │
└────────────────────────────────────────────────────┘
```

#### 三个 session 完全隔离

| Session | 上下文来源 | 生命周期 |
|---------|-----------|---------|
| 被动对话 | 用户消息 + agent 回复 | 用户主导 |
| 主动推送 | alerts / content / drift | scheduler 驱动 |
| 兴趣展开 | scheduler seed + 用户追问 | 用户点击触发 |

#### 交付模式设计

SchedulerService 增加 `DeliverStrategy` 接口，三种 adapter：

| Strategy | 行为 | 适用场景 |
|----------|------|---------|
| `ImmediateDeliver` | 直接推送（当前行为） | instant 提醒（喝水、吃药） |
| `QueuedDeliver` | 进 pending queue，等 passive 空闲 | 中等优先级内容 |
| `InteractiveDeliver` | 推送带交互按钮，用户选择后触发新 session | 新闻、天气等 soft 任务 |

`ScheduleTool` 注册时增加 `delivery_mode` 参数，让 AI 决定用哪种策略。

#### [感兴趣] 点击后的两种模式

| 模式 | 行为 | 优势 | 劣势 |
|------|------|------|------|
| 预生成缓存 | soft 任务已跑完 `process_direct`，内容存 pending store，点击后直接作为 seed | 快（秒级响应） | 内容可能过时 |
| 点击时重生成 | pending store 只存 prompt，用户点击时重新触发 `process_direct` | 内容永远实时 | 慢（需等 AI 推理） |
| TTL 混合 | 短时间内用预生成（如 10 分钟内），超过阈值重新生成 | 兼顾时效与速度 | 实现稍复杂 |

建议默认采用 **TTL 混合**，兼顾用户体验和实现复杂度。

## 八、关键设计决策记录

| 决策 | 选择 | 原因 |
|------|------|------|
| 调度方式 | 独立 asyncio loop | 不依赖外部进程，部署简单 |
| 时间精度 | 1 秒 tick | 对于人机交互场景足够，无需毫秒级 |
| 持久化 | JSON 文件 | 轻量，单实例部署足够 |
| 循环依赖 | lambda 延迟解析 | 保持模块构造顺序无关 |
| 上下文隔离 | scheduler 内容不注入被动对话 | 避免 token 浪费、语义漂移、角色混乱 |
| 交付决策 | 用户显式选择是否展开 | 尊重用户意图，零打扰默认 |
