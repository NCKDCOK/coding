# Agent 各模块设计

> 本文档记录构建生产级 Agent 系统时各核心模块的架构设计。
> 内容以**当前主流、生产可用**的实践为准,不绑定任何单一教程实现;教学版的简化做法会标注，但不作为推荐方案。
> 这是一份**活文档**，随讨论持续维护与扩展。

---

## 文档约定

- 每个模块按统一结构组织：**定位与核心抽象 → 数据模型 → 核心机制 → 分层架构 → 关键设计决策 → 生产加固清单**。
- 「教学版」指最小可跑实现，「生产版」指可上线、可扩展、可恢复的实现。
- 新增模块时复用同一结构，保持文档可读性一致。

---

## 贯穿性设计原则

这几条是所有模块共享的底层判断，先于具体设计。

1. **Context Engineering 是第一性约束。** 主 LLM 的上下文窗口是最稀缺的资源。凡是会产生大量中间噪音的工作（探索、长输出、多轮试错），都应隔离到主上下文之外，只回传提炼后的精华。子代理、上下文压缩、后台任务，本质都是这条原则的不同实现。

2. **自主决策 + 硬护栏的二元。** Agent 的控制流交给 LLM 在运行时决策（调哪个工具、何时调）；但「能做什么」（工具集划定的行动空间）和「不准出界」（代码写死的护栏：状态校验、环检测、权限、超时、并发上限）必须由确定性代码保证。**决策越自主，硬护栏越重要。**

3. **Workflow ↔ Agent 是一条光谱，不是二选一。** 流程固定 → 开发期写死编排（确定性、可调试）；流程开放 → 运行时让 LLM 动态规划。生产系统多为混合：主干确定性编排，局部释放自主性。能用确定性解决的，不要上自主 agent。

4. **三层对象必须分离，不能糊成一层：**
   - **工作目标（durable task）** —— 要做什么、谁依赖谁、总体进度。见模块 1。
   - **运行槽位（runtime task）** —— 哪条命令正在执行、跑到哪、结果何时回来。见模块 2。
   - **子代理（sub-agent）** —— 需要独立推理的委托任务。规划中。

## 1. 任务管理系统（Task Management）

### 1.1 定位与核心抽象

管理「工作目标」及其依赖关系。核心抽象一句话：**带持久化的状态机 + DAG 依赖编排，由就绪判断驱动推进**。

它回答三个问题：现在有哪些任务？每个处于什么状态？哪些现在可以开工？

后端对应物：异步任务队列（Celery）、工作流引擎（Temporal / Airflow / Camunda）、Saga 编排。本质都是「把执行进度持久化下来，使任意一步崩溃后能从断点恢复」。

### 1.2 数据模型：TaskRecord

纯数据、可序列化，与执行逻辑分离。

| 字段 | 含义 |
|---|---|
| `id` | 唯一标识 |
| `subject` | 一句话说明任务做什么 |
| `description` | 补充说明 |
| `status` | 当前状态（见状态机） |
| `blocked_by` | 入边：还在等哪些前置任务（依赖） |
| `blocks` | 出边：完成后解锁哪些后续任务 |
| `owner` | 由谁执行（多 agent 协作时用） |
| `result` | 完成产物或摘要 |
| `error` | 失败时的错误信息 |
| `retry_count` | 已重试次数 |
| `created_at` / `updated_at` | 时间戳 |

### 1.3 状态机

合法状态：`pending → in_progress → completed`，加 `failed`、`deleted`。

| 当前状态 | 允许转移到 |
|---|---|
| `pending` | `in_progress`, `deleted` |
| `in_progress` | `completed`, `failed`, `deleted` |
| `failed` | `pending`（重试）, `deleted` |
| `completed` | `in_progress`（极少数：验收不过重开） |
| `deleted` | —（终态） |

要点：**所有状态变更都过转移表校验，非法转移直接拒绝**——这才让它成为状态机，而非一个 status 字段。「重试」= `failed → pending` + `retry_count++`，不引入独立的 `retrying` 态，保持状态机简洁。

### 1.4 依赖图（DAG）

任务间依赖构成有向无环图。

- **双向边**：`blocked_by`（入边）+ `blocks`（出边）同步维护。正查反查均 O(1)。
- **就绪判断（拓扑核心）**：`is_ready = (status == pending) and 所有前置已 completed`。这是整个系统的灵魂——任务系统的价值不是「存清单」，而是「判断何时能开工」。
- **环检测**：加边时做 cycle detection（从目标节点沿依赖向上 DFS，若能回到自己即成环）。DAG 必须无环，否则循环依赖死锁。在**自主式 agent 中环检测是必需安全阀**，因为 LLM 动态加边可能生成环。
- **fan-out / fan-in**：一个任务拆多个、多个汇一个，由 DAG 自然表达。

后端对应：Airflow DAG、CI/CD pipeline 的 stage 依赖、Spring Batch step 依赖。

### 1.5 持久化与存储选型

> 教学版常用「一任务一文件 JSON」，可读、好调试，但并发写有竞态、无事务。生产按规模选型：

| 规模 | 方案 | 说明 |
|---|---|---|
| 单机起步 / 可读优先 | JSON 文件 | 简单，适合本地调试；无并发保证 |
| 单机生产 | **SQLite** | 一个文件、零运维，但有事务、原子更新、SQL 查询。推荐起点 |
| 多实例 / 高并发 | PostgreSQL | 状态用列、`context` 用 JSONB；靠事务解决竞态 |
| 高吞吐分发 | Redis / 消息队列 | 状态 + 队列分发；注意持久化配置（RDB/AOF） |

**存储层必须抽象成接口**（`save / load / all / next_id`），换实现时上层逻辑零改动。

### 1.6 分层架构

自下而上，每层职责单一：

1. **数据模型层** — TaskRecord（任务是什么）
2. **状态机层** — 状态集合 + 合法转移校验（怎么流转）
3. **依赖图层** — DAG：就绪判断 + 环检测（谁先谁后）
4. **存储层** — 持久化抽象（状态放哪）
5. **管理器层** — 组合上述，提供 create/start/complete/fail/retry/add_dependency/ready_tasks/recover
6. **工具接口层** — 暴露给 LLM：`task_create / task_list / task_get / task_update`，异常作为结果返回让模型自纠

### 1.7 关键设计决策

- **解锁方式**：完成时「物理移除前置依赖」（简单，但丢失原始依赖图结构）vs「保留依赖、就绪时查前置状态」。**生产推荐后者**——依赖结构完整保留，环检测与任务图可视化任何时候都有效，且 `complete` 无需回写多个文件。
- **DAG 谁来画**：编排式（开发期写死）vs 自主式（运行时 LLM 动态加边）。取决于流程是否固定。
- **幂等性**：`complete/fail` 等操作应可重复执行不产生副作用，便于崩溃后安全重放。

### 1.8 生产加固清单

- [ ] 启动恢复：扫描 `in_progress` 残留任务，重跑或标记中断，避免僵尸任务。
- [ ] 并发控制：多实例修改同一任务需事务或乐观锁。
- [ ] 可观测性：任务状态、耗时、卡点可外部查询（dashboard / 日志）。
- [ ] 重试上限 + 退避策略，避免无限重试。
- [ ] 审计：保留状态变更历史（谁、何时、从什么态到什么态）。

## 2. 后台任务系统（Background Tasks）

### 2.1 定位与核心抽象

把「慢执行」移出主循环，让主循环继续推进。核心抽象一句话：**一个 fire-and-forget 的执行器 + 一条回合制的通知回流通道 + 一套防止它污染上下文 / 拖垮机器的护栏**。

**关键认知（与后端异步最大的不同）**：LLM 主循环是**回合制**的，不能被异步回调「唤醒」。所以结果不能 push 回模型，只能由主循环在**下一轮开始前主动 drain 通知队列**带回去——是轮询，不是 callback。

> 难点不在「执行」（开线程跑命令很简单），而在「结果如何节制地回到一个回合制、上下文有限的主循环」。

### 2.2 数据模型：RuntimeTaskRecord

记「运行槽位」，与模块 1 的 TaskRecord（工作目标）是**两层对象**。

| 字段 | 含义 |
|---|---|
| `id` | work id，唯一标识 |
| `command` | 正在执行的命令 |
| `status` | running / completed / failed / timeout / cancelled |
| `started_at` | 开始时间 |
| `result_preview` | 回主循环的简短摘要 |
| `output_file` | 完整输出落盘路径 |
| `durable_task_id` | 关联回模块 1 的工作目标 |
| `pid` / handle | 用于取消跑飞的任务 |
| `exit_code` | 退出码 |

### 2.3 运行状态机

`running → completed / failed / timeout / cancelled`。

比模块 1 简单：基本是**单向到终态，无重试回边**。重试不在这层——重试 = 在模块 1 层面新开一个 runtime task。一个 durable task 可对应多次 runtime task。

### 2.4 执行器

- `run(command)` 立刻返回 `task_id`（fire-and-forget），把 subprocess 甩到旁路执行线。
- **执行载体选型**：mini 用 `daemon` 线程；要隔离「任务崩溃带垮主进程」用子进程；要扛并发量上线程池/进程池 + 队列；跨机分布式再上外部 worker（Celery / 消息队列）。**别一上来就池化。**
- 执行时：全输出写 `.log` 文件，截断摘要写 `result_preview`，状态写 RuntimeTaskRecord。

### 2.5 通知回流通道（架构灵魂）

- 后台完成 → 写一条 notification（`task_id` + `status` + `preview`），**不直接塞全文**。
- 主循环每轮调模型前 `drain_notifications()` → 注入 messages。
- **回流策略**：push（每轮主动注入）vs pull（模型主动 check）。**生产推荐混合**——完成时主动通知一次（模型不漏结果）+ 允许模型随时 `background_check`（主动确认）。纯 push 任务多时刷屏污染上下文，纯 pull 依赖模型记得查。

后端类比：消费者轮询 result queue（而非注册 callback），因为消费者是回合制上线的。

### 2.6 产物存储

**通知负责提醒，文件负责存原文。**

- 完整输出（可能数万行）写磁盘：`.runtime-tasks/<id>.log`。
- 运行状态写：`.runtime-tasks/<id>.json`。
- 通知只带摘要 + 文件引用；模型要看全文再调 `read_file`。

后端类比：消息体不放大 payload，只放对象存储引用（如 MinIO / S3 的 key）。

### 2.7 工具层与主循环集成

- **工具层**：最小 `background_run` / `background_check`；生产加 `background_list`（看在跑的）、`background_cancel`（终止跑飞任务，依赖存了 pid/handle）。
- **主循环集成**：每轮固定前置步骤 = 先 drain 通知 → 注入 → 再调模型；`background_run` 立刻返回不阻塞。
- **核心心智**：主循环仍只有一条，**并行的是等待与执行槽位，不是主循环本身**。

### 2.8 关键设计决策

- **护栏由代码兜底，不交给 LLM**：超时、输出大小截断、并发上限、危险命令拦截（接权限系统）。「开什么后台任务」是 LLM 自主决策的 tool，但「跑不飞、撑不爆上下文、删不了不该删的东西」必须代码保证。
- **与模块 1 的回写**：后台命令完成后，顺 `durable_task_id` 把对应工作目标推进到相应状态。三层咬合成系统的关键。

### 2.9 生产加固清单

- [ ] RuntimeTaskRecord 落盘 + 启动恢复（daemon 线程随进程退出即丢，需标记中断状态）。
- [ ] 超时 + 强制终止，防任务挂死。
- [ ] 输出截断上限，防日志撑爆磁盘/上下文。
- [ ] 并发上限，防 LLM 一次开过多后台任务拖垮机器。
- [ ] 取消机制（kill by pid/handle）。
- [ ] 可观测性：当前在跑、已完成、失败的任务一览。
